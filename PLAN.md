# PLAN.md — Дальнейшее развитие penpen

## Текущее состояние (февраль 2026)

Реализовано:
- Отправка текста, фото, медиагруппы, видео в каналы и чаты
- Несколько получателей (`--to toto test`), параллельная отправка
- Retry-логика (3 попытки, exponential backoff)
- Скачивание YouTube-видео (yt-dlp, H.264 MP4, cover.jpg)
- Управление: `--pin`, `--unpin`, `--delete`, `--edit`, `--reply-to`, `--forward`
- Парсинг REF: число, `t.me/c/...`, `t.me/username/...`, `last`
- Трекинг `message_id` в `.last_message_id.<target>`
- Уведомления админу: ошибки + overflow в raw-тексте (plain text, читаемо)
- Raycast-интеграция (`raycast-send.sh`)
- Шаблоны: `--template NAME --data data.yml` (Jinja2 + YAML, `templates/*.md`)

## Приоритет 1: Inline-кнопки (`--buttons`)

Поддержка inline keyboard через JSON-файл рядом с `message.md`:

```json
[
  [{"text": "Читать", "url": "https://example.com"}],
  [{"text": "Поделиться", "callback_data": "share"}]
]
```

```bash
uv run bot send --to toto --buttons buttons.json
```

URL-кнопки работают без живого бота. `callback_data` потребует FSM-бота (Приоритет 4).
Нужно: `InlineKeyboardMarkup` в aiogram, новый параметр CLI, чтение JSON.

## Приоритет 2: `--poll` — создание опроса

```bash
uv run bot send --to toto --poll poll.json
```

`poll.json`:
```json
{
  "question": "Как вам?",
  "options": ["Отлично", "Нормально", "Плохо"],
  "is_anonymous": true
}
```

Использует `bot.send_poll()` вместо `send_message`.

## Приоритет 3: Веб-морда + Docker

Простой веб-интерфейс для управления ботом с сервера. Нужен для удалённой работы без Raycast/CLI.

**Стек:** FastAPI + Jinja2 templates + vanilla JS, Docker + docker-compose.

**Функции UI:**
- Написать и отправить сообщение (textarea с markdown, выбор таргетов)
- Прикрепить медиа (загрузка файла или YouTube URL)
- Pin / unpin / delete / edit существующих сообщений
- История отправленных (из `.last_message_id.*`)
- Загрузить `cookies.txt` через браузер (без scp)
- Простая авторизация по паролю (`WEB_PASSWORD` в `.env`)

**Архитектура:**
```
web/
├── app.py              # FastAPI, импортирует bot/* напрямую
├── templates/
│   ├── login.html
│   └── index.html
└── static/app.js

Dockerfile              # python:3.12-slim + ffmpeg + deno + uv
docker-compose.yml      # volume для media/, .env, cookies.txt
```

**Новые переменные .env:** `WEB_PASSWORD`, `WEB_SECRET_KEY`

**Сложности:**
- YouTube download блокирует event loop → нужен background task
- deno в Docker — отдельный шаг установки
- `cookies.txt` на сервере: volume + кнопка загрузки в UI

## Приоритет 4: Диалоговый FSM-бот

Бот принимает сообщения в личку и публикует в канал через диалог.
Требует постоянно запущенного процесса — логично деплоить вместе с Docker (Приоритет 3).
Один токен `BOT_TOKEN`, доступ только для `ADMIN_CHAT_ID`.

**Диалог:**
```
Пользователь: [текст]
Бот: "Добавить медиа?" [📷 Фото/видео] [🎬 YouTube] [➡️ Пропустить]
  → файлы: бот скачивает в media/, потом [Готово]
  → YouTube: бот ждёт ссылку
Бот: "Куда публиковать?" [toto] [test] [cat]   ← динамически из config
Бот публикует → "✅ Опубликовано в toto #194"
```

**Новые файлы:**
- `bot/fsm.py` — States + handlers (aiogram Router + FSMContext)
- `bot/runner.py` — запуск long polling с Dispatcher

**Переиспользует без изменений:** `TelegramClient`, `media_scanner`, `markdown_processor`, `message_store`, `config`

**Сложности:**
- Альбомы от пользователя приходят как отдельные сообщения с одним `media_group_id` → нужна группировка с задержкой ~0.5s

## Приоритет 5: Отложенные посты

Публикация в заданное время. Логично делать поверх FSM-бота (Приоритет 4) — там уже есть живой процесс.

**Через FSM-бот:** в диалоге добавить шаг "Когда опубликовать?" → задача сохраняется в SQLite → scheduler в asyncio публикует по времени. Уведомляет в личку: "✅ Опубликовано #194".

**Через CLI** (проще, но процесс должен жить): `--schedule "+2h"` → `asyncio.sleep()` → отправка.

## Идеи для будущего

- **`--list-targets`** — вывести список каналов/чатов из `.env`. Тривиально (10 строк).
- **Статистика канала** — получить число подписчиков через `getChatMemberCount`, показывать после отправки или по команде.
- **Превью перед отправкой** — `--dry-run` уже есть, но можно слать превью прямо в личку админу через FSM-бота: "Вот как будет выглядеть пост, отправляем?"
- **Реакции на пост** — после публикации бот ставит реакцию (👍) на свой же пост в канале через `setMessageReaction`. Маркер что пост свежий.
- **Кросс-постинг из других каналов** — `--forward` уже есть, но можно автоматизировать: подписаться на канал-источник и пересылать посты по правилу (ключевые слова, теги).
- **Экспорт истории** — сохранять лог отправленных постов в JSON/CSV с датой, текстом, таргетом и `message_id`.

## Не делать

- CI/CD интеграция — не нужна для личного инструмента
- Webhook вместо long polling — усложняет деплой без видимых преимуществ для одного пользователя
- Полноценная БД — SQLite только если нужны отложенные посты, иначе избыточно
